Setting the Scene
The University of Northampton wants a new website.
An in-house designer has created the HTML and CSS.
This layout has been signed off by the university and must be used.
The main purpose of the website is to allow university staff to advertise courses available at the university within subject areas.
There must be a secure admin area where staff can log in and add courses which then appear on the public website.

Two Main Tasks
1. Implement the requested functionality on the website.
2. Build the website so it is easy to maintain and reuse in future.
Additional marks are available for reusable components that could be used on future websites.

Important Context
The staff who use the website have basic computer skills but are not programmers.
They must be able to amend content without writing code.
The product manager has chosen a kanban style development process.
The assignment is organised around tickets.

Ticket NMP-0001: User Accounts
Goal:
Create a page using the supplied layout that allows staff members to log in with a username and password.
There must also be a superadmin account that can add and remove staff accounts.
Normal users must not be able to manage staff accounts.

Acceptance Criteria:
- A superadmin can log in and add new accounts.
- Once a new account is added, that user can log in and add subject areas and courses.
- A superadmin can delete accounts.
- The superadmin account cannot be deleted.
- Normal users cannot add or remove accounts.

Implementation Guidance:
- User roles such as superadmin and normal user should be tracked in the database.
- Password security must be considered.
- There should be no passwords in code.
- The solution should be built so new roles can be added in future.
- Using entities and an ORM is recommended.
- Try to combine add and edit forms.

Ticket NMP-0002: Add / Display Subject Areas
Goal:
Logged-in admin users should be able to add, edit, and delete subject areas.
Subject areas should appear in the public website menu.
Clicking a subject area should go to a page showing that subject area heading and eventually its courses.

Acceptance Criteria:
- Logged-in admin users can add, rename, and delete subject areas.
- Users who are not logged in cannot add, edit, or delete subject areas.
- Once a subject area is added, it appears in the menu as a clickable link.
- Clicking a subject area opens a page with the heading of that subject area.

Implementation Guidance:
- Avoid separate add and edit pages if possible.
- Support any number of subject areas.
- Logged-in admins need a way to view existing subject areas and edit/delete them.
- Using entities and an ORM is recommended.

Ticket NMP-0003: Add / Display Courses
Goal:
Logged-in admin users should be able to add courses to subject areas.

Each course should:
- be assigned to a subject area
- have a title
- have a length in years
- have a type such as MSc, BSc, MA, BA
- have a description
- have a list of modules with module code, title, and short description

Once added, the course should appear on the public website on the relevant subject area page.

Acceptance Criteria:
- Courses can be added with all required data.
- Courses can be edited or updated.
- Courses can be moved from one subject area to another.
- Courses are visible on the public side of the website in the relevant subject area.

Implementation Guidance:
- Avoid separate add and edit pages.
- Support any number of courses.
- Logged-in admins need a way to manage courses.
- Consider a proper structure for modules rather than storing them as a single text field.
- Using entities and an ORM is recommended.

Ticket NMP-0004: Enquiries
Goal:
Visitors should be able to submit enquiries using the website.
Admins should be able to view them when logged in.
Enquiries need to be tracked as pending or responded to.

Required enquiry fields:
- Name
- Email address
- Phone number (optional)
- Course name
- Enquiry text

Acceptance Criteria:
- Anyone can submit an enquiry.
- Submitted enquiries are visible to logged-in admins.
- Enquiries can be marked as responded to.
- The system logs which logged-in user responded.
- There is a way to show pending enquiries.
- There is a way to show responded enquiries.

Implementation Guidance:
- Use one feature/page structure where possible for pending and responded lists.
- The "who responded" value must come from the logged-in user for security.
- Using entities and an ORM is recommended.

Ticket NMP-0005: Course Search
Goal:
Users should be able to search courses by:
- subject area
- type
- duration in years (minimum and maximum)

Users may search using one, two, or all three criteria.

Acceptance Criteria:
- Users can search by type.
- Users can search by subject area.
- Users can search by duration.
- Users can search using one, two, or all three criteria.

Implementation Guidance:
- Reuse as much of the subject area course-list page as possible.
- Search should be done in the database, not filtered in PHP.
- If using an ORM, extend it to support multi-field searching.

Ticket NMP-0006: Part-Time Courses
Goal:
Courses should be able to be marked as available part-time.
The public site should show whether a course can be completed part time.
Search should also support filtering for part-time courses.

Acceptance Criteria:
- Add/edit course forms include a part-time option.
- Subject area course pages show whether a course can be completed part time.
- Search results show whether a course can be completed part time.
- Search supports filtering to only show part-time courses.

Implementation Guidance:
- Existing courses should remain backward compatible.
- Existing records can assume part time = no until updated.

Ticket NMP-0007: Pagination
Goal:
Subject area pages and search results should show 10 courses per page with page links.

Acceptance Criteria:
- Subject area pages show 10 courses per page with clickable page numbers.
- Search results also support pagination.

Implementation Guidance:
- Reuse the same list structure for subject area pages and search results where possible.
- Do pagination in the database using LIMIT and OFFSET.
- For testing, a lower threshold can be used temporarily, but final submission should use 10 per page.

Marking Rubric Overview
The rubric is split into:
- Functionality (50%)
- Code Quality (50%)

Functionality (50%)
This is based on how many acceptance criteria across the tickets are met and whether the website works correctly.
Lower grades apply where fewer acceptance criteria are met or where core functionality is broken.
Higher grades apply as more acceptance criteria are met.

Code Quality (50%)
Code quality is capped by functionality.
A broken system cannot achieve a high code-quality mark even if the code structure is good.
Code quality considers:
- reducing repetition
- use of reusable layout/components
- password security
- separation of concerns
- avoiding repeated bootstrap code
- avoiding separate add/edit pages where possible
- single entry point and controllers
- use of objects and classes
- database abstraction
- autoloading
- namespaces
- reusable architecture that can be moved to another site without modification
